# Ordering and packed-start benchmarks — 2026-09-09 (PDT)

Mutation throughput: **+14.3% from the ordering PR**, then **+4.7% from packing
pending starts** (median within-round changes).

Action throughput: **+13.6% from the ordering PR**, then **+7.3% from packing
pending starts** (median within-round changes).

All 183,000 tasks succeeded: 3,000 smoke-check tasks, 90,000 warmup tasks, and
90,000 measured tasks. No throughput run timed out, and captured runtime logs
contained no execution errors. During mutation round 3, a cleanup cursor skipped
one completed row with a tied creation time. The driver stopped before the next
arm; another cleanup pass cleared it and the driver resumed from the next
unmeasured run. This lengthened the gap within that round; its timings remain
included. The cleanup helper was subsequently fixed with pagination cursors and
a regression test (175 tests pass).

Keep the PRs separate: ordering improved throughput in every measured round.
Packing consistently reduced document work and enqueue time, but its mutation
throughput change ranged from -4.9% to +10.3%; treat that timing gain as
tentative.

## Method and scope

This compares the stack's three component revisions with a common client and
harness, on `dev:precious-raven-853`:

| Variant  | Revision  | Change                                                                                               |
| -------- | --------- | ---------------------------------------------------------------------------------------------------- |
| Baseline | `9a64c83` | `main`, version 0.4.11                                                                               |
| Ordering | `0b0b60e` | [#220](https://github.com/get-convex/workpool/pull/220), commit/snapshot ordering and cursor changes |
| Packed   | `387a3ae` | [#234](https://github.com/get-convex/workpool/pull/234), multiple pending starts per document        |

Harness: `95d074c`, with the archived mount-selection patch. Dependencies:
Convex 1.43.0, batch-worker 0.2.2, convex-helpers 0.1.111; Node 24.20.0. The
three components were copied into an isolated checkout, mounted fresh, built,
and successfully deployed before any measurements. Their source was unchanged
during the experiment. The baseline here is **0.4.11**, not the published 0.4.9
package used in the September 8 report.

Every full run enqueues 5,000 tasks in batches of 100, with a 50 ms inter-batch
gap and parallelism 200. Mutations have no artificial workload; actions sleep 20
ms. All variants first passed a 1,000-mutation smoke check. Each workload then
gets three discarded warmups per variant followed by three measured rounds.
Warmup order is B/O/P, O/P/B, P/B/O; measured order is P/O/B, O/B/P, B/P/O. Each
variant occupies every position once in each phase. Runs are serial, with all
three components drained and app bookkeeping cleared between arms.

Throughput is tasks divided by time from run start through the final completion
callback. Enqueue time includes batch RPCs and configured gaps. Latency is
per-task enqueue to completion callback; table p95s are medians of run-level
percentiles. Polling and completion bookkeeping are part of the measured load.

These are descriptive results from three rounds, with separate component storage
histories and time-varying deployment load. They isolate the two PR layers, not
individual lines within the ordering PR. Immediate bulk throughput does not
establish scheduled-work correctness or light-load tail latency. Do not compare
absolute rates directly with measurements from another day.
